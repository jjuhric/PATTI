## How to use this doc

Work top to bottom within "Phase 0" first — those are live security holes reachable by any
registered user today, not theoretical. After that, phases are ordered by risk/value but are
independent; pick whatever fits the token budget you have.

## Phase 0 — Close the open RCE chain (do first)

These three combine into: **any account (and registration is open to anyone who can reach the
server) can get arbitrary code execution on the host machine via plain REST calls**, with no
admin check and no human-in-the-loop gate. On a LAN-exposed personal assistant this is the
highest-value fix available.

- [x] **SEC-1** [CRITICAL] Command injection in `host_machine_tool`, reachable via a REST route
  with no admin check. *Done: added a strict `service` name validator (rejects anything outside
  `[a-zA-Z0-9_.-]`) applied in `get_service_status`/`get_journal_logs`/`restart_service`, and
  gated `/api/host/service/restart` + `/api/host/gpio/run` behind `requireAdmin`. Tests:
  `backend/tests/host_machine_tool.test.js` (new), `backend/tests/host.test.js` (updated).*

- [x] **SEC-2** [CRITICAL] Upload-a-script-then-execute-it RCE chain. *Done: `run_script` now
  refuses any resolved path under `chat_attachments/`, and the route it's reachable through
  (`/api/host/gpio/run`) is admin-gated as part of SEC-1. Test:
  `backend/tests/host_machine_tool.test.js`.*

- [x] **SEC-8** [MEDIUM, but multiplies SEC-1/SEC-2] Self-registration is fully open. *Done:
  the first account on a fresh instance becomes admin automatically and can always self-register
  with no code; every account after that requires `REGISTRATION_INVITE_CODE` to match (unset =
  closed by default). Added `POST /api/admin/users` so the admin can onboard accounts directly
  without an invite code. Tests: `backend/tests/auth.test.js`, `backend/tests/admin.test.js`
  (updated). Follow-up: `REGISTRATION_INVITE_CODE` set in `.env` to a generated random value,
  and a "Create User" button + modal added to `AdminDashboard.jsx`'s Users section, calling
  `POST /api/admin/users`. Test: `frontend/src/components/AdminDashboard.test.jsx` (new).*

  created during normal delegation. Tests: `backend/tests/pendingApprovals.test.js` (new, 9),

- [x] **SEC-4** [HIGH] SSRF via chat-driven web-fetch tools. *Done: added
  `backend/utils/ssrfGuard.js` (`assertPublicHttpUrl`) - resolves the hostname and rejects
  loopback/RFC1918/link-local/CGNAT/multicast addresses (including the 169.254.169.254 cloud
  metadata address) before any fetch. Wired into `fetchPageText` (`web_extract.js`),
  `blindScrapeUrl` (`web_search_tool.js`), and `fetchAndClean` (`deep_research_tool.js`) - the

  mock `ssrfGuard` so they don't depend on real DNS/network (see note in those test files).*

- [~] **SEC-5** [MEDIUM] JWT accepted via query string (`?token=`), 30-day expiry, no revocation.
  *Partially done - real revocation added.* `?token=` in the URL is load-bearing for
  EventSource/WebSocket/`<img src>`/`window.open` calls (SSE alert stream, LM Studio log
  stream, RPi terminal WebSocket, DB backup download, attachment thumbnails, the monitor
  dashboard link) - none of those browser APIs can send a custom `Authorization` header, so
  removing the query-string token means migrating to httpOnly-cookie auth, the same larger
  change SEC-6 below needs. **Did not attempt that today** - it touches ~12 frontend files, the
  CORS/CSRF posture, and every stream/socket endpoint on live production auth; wanted a
  deliberate, tested pass rather than a blind swap on a system you use daily.
  **What's done instead:** real server-side revocation, which was the actual point of "a leaked
  30-day token has no recourse." Added `users.tokens_valid_after` (`schema.sql` + a `db.js`
  migration for existing installs), checked in `authenticateToken`
  (`backend/middleware/auth.js`) against the token's `iat`, and a new
  `POST /api/auth/logout-everywhere` (`backend/routes/auth.js`) that sets the cutoff to now.
  Wired up a "Log out everywhere" button under a new Security tab in
  `frontend/src/components/ProfileModal.jsx`. Expiry left at 30 days (no UX regression) since
  revocation now covers the leak scenario. Tests: `backend/tests/auth.test.js` (3 new),
  `frontend/src/components/ProfileModal.test.jsx` (3 new). Full suites green (backend 99/1165,
  frontend 20/118).*
  **CI-caught follow-up fix:** the revocation check compared `iat * 1000 < tokens_valid_after`
  (strict less-than) against a SQLite `CURRENT_TIMESTAMP` cutoff, both whole-second precision.
  On a fast CI runner, login and the immediate `logout-everywhere` call could land in the same
  second, making the comparison false and letting the just-revoked token stay valid -
  intermittent, not reproducible locally on a slower machine. Fixed to `<=` in
  `backend/middleware/auth.js` so a token issued in the same second as the cutoff (including the
  token that made the revocation call itself) is correctly treated as revoked. Verified with 3
  repeated local runs of `auth.test.js` plus the full backend suite (101/1205, all green).

- [x] **BUG-15** [newly found, 2026-08-03] `restart_service`'s Windows path
  (`Stop-ScheduledTask` then `Start-ScheduledTask` against `PATTI-Assistant`,
  `backend/tools/host_machine_tool.js:288-292`) does not reliably restart the process.
  Confirmed live while restarting production for this session's changes:
  `Stop-ScheduledTask` does not kill the underlying `node.exe` - it's launched by
  `run-background.vbs`'s `WshShell.Run ..., 0, true` loop, which survives the task being marked
  stopped. `Start-ScheduledTask` then starts a *second* `node.exe` that immediately crashes with
  `EADDRINUSE` on port 3000, and the VBS loop retries every 5 seconds against the still-alive
  original process indefinitely (confirmed via the log: repeated `EADDRINUSE` crashes every
  ~5-6s). Net effect: calling PATTI's own "restart yourself" capability does nothing useful -
  the old process keeps serving (stale code) while a crash-loop burns CPU in the background
  until someone manually finds and kills the original PID.
  **Fix:** `run-background.vbs`'s loop needs to actually be interruptible - e.g. have
  `restart_service` kill the tracked `node.exe` PID directly (by matching
  `CommandLine -like '*backend/server.js*'`) instead of going through
  `Stop-ScheduledTask`/`Start-ScheduledTask`, or rewrite the VBS wrapper so stopping the task
  actually terminates its child. Documented the manual workaround in
  `docs/IMPLEMENTATION_PLAN.md` §6 in the meantime. **Effort: S-M.**
  *Done (2026-08-06): took the "kill the tracked PID directly" route rather than rewriting the
  VBS wrapper - rewriting `run-background.vbs` to make itself interruptible is a deeper,
  harder-to-verify change to the exact mechanism keeping PATTI alive across crashes/reboots, and
  it wasn't necessary to fix the actual bug. New `backend/scripts/restart_patti_service.ps1`
  stops the scheduled task, explicitly finds and kills any `node.exe` whose command line matches
  `*server.js*`, waits briefly, then starts the task fresh - closing the race instead of just
  documenting it. `backend/tools/host_machine_tool.js`'s `restart_service` action now runs this
  script instead of the bare stop/start pair; the manual procedure in
  `docs/IMPLEMENTATION_PLAN.md` §6 was updated to match, with the old fully-manual steps kept as
  a fallback. Verified twice against the real production instance: manually confirmed the exact
  failure mode still reproduces (`Stop-ScheduledTask` leaves the old PID alive), then ran the new
  script directly - it correctly found and killed the stale PID, and the task came back up as a
  single clean process (`Express Backend running securely on port 3000`, no `EADDRINUSE`, no
  retry-loop noise in the log). 2 new tests in `backend/tests/host_machine_tool.test.js`
  (`os.platform` mocked to `win32` so the assertions hold regardless of which OS actually runs

## Phase 3 — Context, token, and reasoning management enhancements

- [x] **ENH-1** No token-accurate counting anywhere - fell back to `Math.ceil(text.length / 4)`
  whenever a provider didn't report real usage. *Done: added the `gpt-tokenizer` package (pure
  JS, no native/WASM deps) and `backend/utils/tokenAccounting.js`'s `estimateTokens()` - a real
  BPE token count (cl100k_base encoding) instead of a character-based guess, with a length/4
  fallback only if tokenization itself throws. Not a perfect match for every provider's own
  tokenizer, but far closer than length/4 for any modern BPE-based model. Tests:
  `backend/tests/tokenAccounting.test.js` (new, 8 tests, including one proving the estimate is
  real tokenization and not disguised character math).*

- [x] **ENH-2** Token-usage logging duplicated across all 10 call sites found (near-identical
  `INSERT INTO token_usage ...` blocks differing only in fallback estimator - more than the 6
  originally estimated). *Done: same `tokenAccounting.js` module also exports `logTokenUsage()`,
  now used at every site across `backend/utils/agents.js` (6), `backend/utils/llm_text.js` (2),
  `backend/llm/local_stream.js` (2), and `backend/llm/gemini_stream.js` (1) - replacing ~90 lines
  of duplicated `db.run(...).catch(...)` boilerplate with one call each. Bonus: two sites in
  `llm_text.js` previously swallowed logging failures completely silently (`.catch(() => {})`,
  not even logged) - now go through the same error-logged helper as everywhere else. Full backend
  suite: 100 suites / 1181 tests, all green.*

- [x] **ENH-3** No prompt caching - the Supervisor's system prompt was re-sent verbatim on
  every one of up to 10 turns within a single request with no `cache_control`. *Done: added
  `buildAnthropicSystem()` to `backend/llm/provider_config.js` - splits `system` into a cached
  prefix block (`cache_control: {type: "ephemeral"}`) plus an uncached remainder, used by both
  `buildBody` and `buildStreamBody` via a new optional `cacheableSystemPrefix` param (Anthropic
  only; a no-op, unchanged-behavior string for every other apiStyle). Threaded through
  `runAgentTurn`/`runSupervisorTurn` via `settings.cacheableSystemPrefix`, and wired up at the
  actual hot path: `backend/services/agent_loop.js`'s Supervisor loop now captures
  `AGENT_PROMPTS.supervisor` once (`supervisorBasePrompt`) and marks it as the cacheable prefix
  on every turn - both avoiding re-invoking the prompt-customization loader's filesystem reads on
  every one of up to 10 turns, and guaranteeing the prefix-match holds for the cache split.
  Falls back safely to the plain uncached string if the prefix ever doesn't actually match (e.g.
  customizations changed mid-request). Tests: 9 new across
  `backend/tests/provider_config.test.js` (`buildBody`/`buildStreamBody`/`buildAnthropicSystem`
